# UniTest 구현

UniTest의 구현은 상태를 재현하는 노드와 동작을 검증하는 Lab을 프로젝트의 실행 흐름으로 연결한다.

## 목차

1. 구성 요소의 책임
2. Lab과 상태 조합
3. 노드 생성과 이력 재현
4. 프로젝트의 실행과 종료
5. 결과 스냅샷과 JSON

## 1. 구성 요소의 책임

| 구성 요소 | 보유 정보 | 책임 |
| --- | --- | --- |
| `Model` | Subject, 기대 상태, MetadataGroup, 실행 이력과 지속·계속 가능 상태 | 대상 상태와 테스트가 기대하는 상태를 보관한다. |
| `Lab` | Id, 준비·동작·검증 함수와 메타데이터 템플릿 | 한 동작의 AAA 검증과 실행 제한 반영을 수행한다. |
| `CompositeLab` | 순서가 있는 Lab 목록 | 여러 상태 축의 준비와 검증을 원본 동작에 결합한다. |
| `Node` | 모델, Lab, 부모·자식, 결과와 진단 값 | 독립된 경로 상태와 실행 결과를 유지한다. |
| `Project` | 실행 정책, 큐, 작업자와 취소 상태 | Lab 생성·실행을 조정하고 시작한 작업의 종료를 보장한다. |
| `TestReport` | 값으로 복사한 노드 목록 | 실행 객체와 분리된 JSON 출력 데이터를 제공한다. |

세부 호출 예제와 테스트 작성 절차는 [사용법](04-Usage.md)에 둔다.

## 2. Lab과 상태 조합

### 2-1. 단일 Lab

Lab 실행은 모델의 실행 이력 반영과 메타데이터 초기화로 시작한다. Arrange는 템플릿을 복사하고 동작별 메타데이터와 기대 상태를 준비한다. Act는 실제 대상을 호출하고, Assert는 실제 상태와 기대 상태를 비교한다.

지정한 예상 예외가 발생해도 현재 Lab의 Assert를 수행한다. 예상 예외가 발생하지 않거나 예상과 다른 예외가 발생하면 실패로 기록한다. 단계별 오류는 `ExecutionException`으로 반환하며 후속 실행을 중단한다.

`ToUncontinuable`, `ToUnsustainable`과 남은 실행 횟수는 현재 검증을 마친 뒤 반영한다. 특히 `ToUncontinuable`은 현재 Assert를 생략하는 설정이 아니다.

### 2-2. Merge와 Extend

Merge는 복사한 Lab에 템플릿의 동작과 메타데이터를 결합한다. Extend는 원본 Lab에 다른 상태 축의 Lab을 덧붙여 CompositeLab을 만든다.

CompositeLab은 원본에서 확장 방향으로 Arrange를 수행하고 원본의 Act만 실행한다. Assert는 확장에서 원본 방향으로 수행한다. 예상 예외는 조합된 메타데이터에서 확인하며, 모든 검증이 성공한 뒤 실행 제한을 합산한다. 남은 실행 횟수에는 가장 작은 제한을 적용한다.

상태 축의 결합 방향은 준비와 검증 순서의 의미를 가진다. 단순히 동일한 함수를 여러 번 호출하는 용도로 확장하지 않는다.

### 2-3. TestCase

TestCase는 동작과 상태 조건의 허용·제외 정의를 가진 읽기 전용 값 형식이다. Append, Confine, Exclude 계열은 새 정의를 반환한다. 생성기는 축별 조건을 좁히면서 실제 동작 템플릿을 선택한다.

## 3. 노드 생성과 이력 재현

루트 노드는 초기 모델을 만든다. 자식 노드는 새 모델에 이전 경로를 재현한 뒤 다음 Lab을 실행할 준비를 한다. 서로 다른 경로의 기대 상태를 같은 모델 인스턴스에 누적하지 않는다.

노드 상태는 준비, 실행, 성공, 실패와 취소를 구분한다. 실패와 취소는 후속 실행 여부에 반영하며, 실행한 모델의 설명과 경로 이력은 진단 값으로 보관한다.

`DetachAndRestore`는 원본 트리를 변경하지 않는 분리된 디버그 노드를 만든다. 분리된 노드의 리포트에도 원래 조상 경로를 포함하며, 다시 분리하거나 자식을 추가해도 이 경로를 유지한다.

Lab ID에 공백·유니코드·문장부호를 사용할 수 있다. `/`는 재실행 경로 구분자이므로 노드 생성 시 거부한다. `Id` 속성의 이름과 그 속성에 저장하는 문자열 값은 구분한다.

## 4. 프로젝트의 실행과 종료

### 4-1. 설계와 실행의 연결

1. 프로젝트가 실행 깊이와 취소 상태를 준비하고 루트 노드를 만든다.
2. TestDesigner가 현재 모델에서 Lab을 생성하고 자식 노드를 실행 대기열에 등록한다.
3. TestExecutor가 준비된 노드를 실행하고 결과와 완료 상태를 등록한다.
4. 조정 루프가 완료한 작업을 회수하고 계속 가능한 노드를 다음 설계 대상으로 넘긴다.
5. 종료 조건에 도달하면 새 작업 등록을 멈추고 시작한 작업을 모두 기다린다.

Lab을 생성하는 도중에도 먼저 준비된 노드는 실행할 수 있다. 생성기의 반복자가 실패해도 이미 생성한 자식을 보존한다. 처리할 일이 없을 때는 작업 등록·완료 신호를 비동기로 기다린다.

### 4-2. 실행 모드

`ThreadPool`은 설계와 실행 작업을 Task.Run으로 전달한다. `Inline`은 Task.Yield 이후 추가 Task.Run 없이 처리한다. 두 모드는 같은 비동기 공개 API와 결과 계약을 사용하며, Inline도 같은 OS 스레드에서의 실행을 보장하지 않는다.

깊이 기반 실행은 여러 경로를 탐색한다. ID 기반 실행은 지정한 경로를 재현한다. 연속 실행은 현재 단계의 후보를 검사한 뒤 이력과 seed에 따른 결정적 선택으로 지속 가능한 경로를 이어 간다.

### 4-3. 취소와 실패

외부 취소와 프로젝트 취소는 연결된 토큰을 통해 작업자에게 전달한다. 실패 중단 정책이 켜져 있으면 실패를 확인한 뒤 새 작업 등록을 중단한다. 이미 시작한 작업의 완료와 예외를 확인한 뒤 동기화 자원을 정리하므로 반환 후 작업자가 결과 트리를 수정하지 않는다.

노드에 기록된 테스트 실패와 취소는 결과 트리에서 확인한다. 노드에 기록되지 않은 비취소 예외는 Execute 호출자에게 전파한다. Run 계열 도우미는 이런 예외를 로깅하고 실패를 반환한다.

## 5. 결과 스냅샷과 JSON

GetReport는 실행 객체를 참조하지 않는 값 스냅샷을 만든다. 노드 목록은 평탄하며 `nodeId`와 `parentId`로 연결된다. 모델 설명, 경로, 예외와 리포트 생성 오류를 각각 보관한다. 모델의 ToString이 실패해도 실행 오류나 자식 노드를 잃지 않는다.

GetFailedReports는 실패 노드와 그 조상을 유지하고 기존 노드 ID를 보존한다. 실패가 없으면 첫 노드만 남긴다. 분리된 디버그 노드의 조상 진단도 같은 구조로 출력한다.

내장 JSON 작성기는 실행 후 문자열과 예외 값을 직렬화한다. 제어 문자와 단독 surrogate를 이스케이프하며, ExportJson은 BOM 없는 UTF-8 파일을 저장한다. JSON 생성을 위한 외부 런타임 패키지는 필요하지 않다.

## 6. 설계와 확장 기준

- 새 테스트 도메인은 Model과 Project를 통해 확장하고, 프레임워크에 도메인별 실행기를 추가하지 않는다.
- 기대 상태는 대상의 실제 결과를 그대로 복사하지 말고 입력과 계약에서 계산한다.
- 동시성 변경은 작업 등록, 완료 관찰, 취소와 자원 정리의 순서를 함께 검증한다.
- 공개 이름이나 동작을 변경하면 샘플·사용 문서·이전 안내와 관련 테스트를 함께 갱신한다.

전체 구조는 [개요](01-Overview.md), 실패 재현과 연속 실행의 선택 기준은 [확장 기능](03-Uni-Test-Extensions.md)을 참고한다.
