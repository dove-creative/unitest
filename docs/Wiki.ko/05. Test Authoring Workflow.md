# UniTest 테스트 작성 워크플로

이 문서는 에이전트가 일반 단위 테스트와 UniTest 기반 자체 테스트를 작성하거나 보강할 때 따르는 작업 흐름이다.

## 목차

1. 모드 선택
2. 테스트 문서 폴더 준비
3. 상태-동작 표 작성
4. 테스트 계획 작성
5. 테스트 코드 작성
6. 빌드와 실행
7. 결과 기록과 통합 테스트

## 1. 모드 선택

테스트 작성 작업을 시작할 때 설계자가 지정한 모드를 먼저 확인한다. 모드가 지정되지 않았다면 안전 모드를 기본값으로 사용한다.

| 모드 | 실패 또는 설계 오류 대응 |
| --- | --- |
| 안전 모드 | 테스트 실패 시 원인과 필요한 수정안을 설계자에게 보고하고 대기한다. |
| 자동 모드 | 테스트 실패 시 테스트 코드 또는 대상 코드를 직접 수정한다. API 변경이 필요한 중대한 설계 오류일 때만 설계자에게 보고하고 대기한다. |
| 위임 모드 | API 변경이 필요한 경우에도 에이전트가 스스로 코드와 문서를 수정하고, 작업이 끝난 뒤 변경 내용과 결과를 보고한다. |

모드는 실패 대응 범위를 정하는 기준이다. 상태-동작 표 작성, 테스트 계획, 테스트 코드 작성, 실행 결과 기록의 기본 흐름은 모든 모드에서 동일하게 유지한다.

## 2. 테스트 문서 폴더 준비

상태-동작 표, 테스트 계획과 실행 결과는 테스트 코드와 분리하여 위키의 테스트 문서 위치에서 함께 관리한다.
문서의 기존 구성에 따라 먼저 기준 폴더를 정한다.

- 객체별 문서가 독립된 폴더에 있다면 그 폴더를 기준으로 한다.
- 객체별 문서가 없으면 가장 가까운 공통 문서 폴더를 기준으로 한다. 설계 문서를 공통 폴더의 개별 파일로 관리하여 독립된 객체별 문서 폴더가 없는 경우에도 같다.
- 여러 객체에 걸친 계획과 전체 결과는 관련 객체의 공통 문서 폴더를 기준으로 한다.

문서는 테스트 구성 방식으로 구분한다. `Unit`은 대상 API를 직접 검증하는 일반 단위 테스트이고,
`UniTest`는 UniTest의 Project와 Lab으로 경로를 생성하고 실행하는 자체 테스트이다.
양쪽 모두 NUnit으로 발견하고 실행할 수 있으므로 NUnit 사용 여부로 구분하지 않는다.

객체별 폴더와 공통 폴더에는 같은 배치 규칙을 적용한다.
기준 폴더에 기존 `Test` 또는 `Tests`가 있으면 이름을 유지하고, 일반 테스트는 `Unit`, 자체 테스트는 `UniTest` 아래에 둔다.
기존 테스트 폴더가 없고 UniTest 기반 테스트만 관리한다면 기준 폴더 바로 아래에 `UniTest`를 생성할 수 있다.
일반 테스트도 관리할 때는 `Tests`를 만들고 두 종류를 나눈다. 이때 기존의 바로 아래 `UniTest`도 `Tests/UniTest`로 옮기고 관련 링크를 갱신한다.
코드 쪽과 문서 쪽의 폴더 구조는 각각 판단한다.

| 기존 구조와 관리 범위 | 일반 테스트 문서 | UniTest 기반 테스트 문서 | 공통 이슈 목록 |
| --- | --- | --- | --- |
| 테스트 폴더가 없고 UniTest 기반 테스트만 관리 | 해당 없음 | `<기준 폴더>/UniTest` | `<기준 폴더>/UniTest/Issues.md` |
| 테스트 폴더가 없고 일반 테스트도 관리 | `<기준 폴더>/Tests/Unit` | `<기준 폴더>/Tests/UniTest` | `<기준 폴더>/Tests/Issues.md` |
| 기존 `Test`가 있음 | `<기준 폴더>/Test/Unit` | `<기준 폴더>/Test/UniTest` | `<기준 폴더>/Test/Issues.md` |
| 기존 `Tests`가 있음 | `<기준 폴더>/Tests/Unit` | `<기준 폴더>/Tests/UniTest` | `<기준 폴더>/Tests/Issues.md` |

공통 위치에서는 대상별 상태표·계획·결과를 `Unit/<대상>` 또는 `UniTest/<대상>`에 묶는다.
같은 객체를 두 방식으로 검증하면 문서도 나누며, 공유하는 계약은 연결하되 각 테스트가 확인한 범위를 따로 기록한다.

이 저장소는 한국어 설계 문서를 `docs/Wiki.ko` 바로 아래 파일로 관리하므로 기존 `Tests`를 공통 문서 폴더로 사용한다.

| 위치 | 관리 대상 |
| --- | --- |
| `docs/Wiki.ko/Tests/Unit/<대상>` | `BlackThunder.UniTest.Tests.Unit`의 일반 테스트 |
| `docs/Wiki.ko/Tests/UniTest/<대상>` | `BlackThunder.UniTest.Tests.Recursion`의 UniTest 기반 자체 테스트 |
| `docs/Wiki.ko/Tests/Result.md` | 두 테스트 프로젝트의 공통 구성과 전체 실행 결과 |
| `docs/Wiki.ko/Tests/Issues.md` | 모든 모듈의 테스트 문제와 후속 확인 지점 |

대상별 문서는 [전체 구성과 결과](Tests/Result.md)에서 연결한다.
테스트 문서는 기본적으로 다음 파일로 나눈다.

| 파일 | 역할 |
| --- | --- |
| `01. Tables.md` | 모듈별 상태-동작 표 |
| `02. Plans.md` | 상태-동작 표와 테스트 파일·메서드의 대응 및 실행 계획 |
| `03. Results.md` | 실행 중 확인한 주요 이슈와 결과 기록 |

기존 테스트를 문서화할 때는 이미 구현된 검증 범위와 앞으로 필요한 보강을 구분한다.
표의 계약 그룹 수와 NUnit 매개변수 전개 후의 실행 사례 수를 혼동하지 않는다.
기존 실행 기록을 재정리한 경우에는 실행 날짜와 근거를 적고, 새로 실행한 결과처럼 표현하지 않는다.

여러 대상이나 두 테스트 종류에 걸친 공통 실행 요약은 공통 테스트 문서 폴더의 `Result.md`에 둔다.
모듈별 상세 표·계획·결함 기록을 복제하지 않고 해당 문서로 연결한다.

테스트 문제를 한눈에 볼 수 있도록 위 표의 공통 위치에 `Issues.md`를 반드시 생성하고 유지한다.
여러 모듈이나 테스트 종류를 함께 관리하면 공통 테스트 문서 폴더의 한 목록으로 모으고, 각 모듈의 상세 결과로 연결한다.
테스트 코드 폴더에는 이 문서를 두지 않는다. 기존 `Test`·`Tests` 이름은 유지하며, 바로 아래 `UniTest`를 `Tests/UniTest`로 옮길 때는 이슈 목록을 `Tests/Issues.md`로 합친다.
이 저장소에서는 [테스트 확인 사항](Tests/Issues.md)을 사용한다. `Result.md`에서 이 목록을 연결하고, 모듈별 결과 문서에서도 관련 항목의 ID와 함께 연결한다.

TRX와 실행 로그는 실제로 실행한 테스트의 범위에 따라 다음 위치에 둔다. 별도의 `Results` 폴더나 저장소 루트의 결과 폴더는 만들지 않는다.

| 실제 실행 범위 | 원본 산출물 위치 |
| --- | --- |
| 일반 테스트의 한 모듈만 실행 | `docs/Wiki.ko/Tests/Unit/<모듈>/`의 문서 옆 |
| UniTest 기반 테스트의 한 모듈만 실행 | `docs/Wiki.ko/Tests/UniTest/<모듈>/`의 문서 옆 |
| Unit 프로젝트 전체 실행의 TRX | `docs/Wiki.ko/Tests/Unit/` 바로 아래 |
| Recursion 프로젝트 전체 실행의 TRX | `docs/Wiki.ko/Tests/UniTest/` 바로 아래 |
| 전체 빌드·통합 실행 로그 | `docs/Wiki.ko/Tests/` 바로 아래 |

명령을 시작한 작업 폴더나 보고서 작성 대상이 아니라 실제 실행 범위로 위치를 정한다.
모듈별 검증과 결과 정리에서는 해당 모듈만 필터로 실행하고, 생성한 TRX와 로그를 그 모듈의 문서 옆에 두는 것이 기본이다.
각 모듈의 `03. Results.md`는 같은 폴더의 자기 모듈 TRX와 로그를 직접 상대 링크로 연결한다.
예를 들어 Lab 결과는 `Tests/Unit/Lab/` 또는 `Tests/UniTest/Lab/` 안에 실제 산출물과 문서를 함께 둔다.

전체 프로젝트의 TRX가 필요한 통합 검증에서는 해당 실행 범위의 위치에 저장한다.
이전 산출물을 정리하여 삭제할 때는 관련 링크도 함께 제거하고, 필요한 실행 수치와 결함 분석만 문서 이력으로 남긴다.
전체 TRX를 특정 모듈에 복제하거나 분할하지 않으며, 필요하면 모듈 문서에서 추가 근거로 연결한다.
전체 TRX의 공유 링크만 추가한 상태를 모듈별 산출물 정리가 완료된 상태로 간주하지 않는다.

파일명은 실행 날짜와 목적을 구분할 수 있도록 정하고, 같은 날짜에 같은 목적으로 반복 실행하면 시간도 포함한다. 예시는 `20261107-001145-unit-all.trx`,
`20261107-001145-model-unit.trx`, `20261107-001145-build.log`이다.
기존 자동 생성 TRX 파일명은 실행 시간을 식별할 수 있으면 유지할 수 있다.
생성 TRX와 로그는 `.gitignore`에서 계속 제외하며, 요약 문서만 원본 산출물의 상대 링크를 제공한다.
이동할 때는 원본 내용과 관련 링크를 함께 보존한다.

## 3. 상태-동작 표 작성

`01. Tables.md` 파일에 각 모듈 또는 유닛의 상태-동작 표를 작성한다. 기존 `01. Tables.md` 파일이 있다면, 현재 구현과 공개 API를 기준으로 내용을 검토하고 보강한다.

상태-동작 표의 형식과 의미는 [UniTest 상태-동작 지침](00.%20Unit%20Test%20Guideline.md)을 따른다.

## 4. 테스트 계획 작성

상태-동작 표를 바탕으로 테스트 코드를 작성하거나 수정하기 전에 `02. Plans.md` 파일을 만든다. `02. Plans.md`는 표의 어떤 칸을 어떤 테스트 파일과 테스트 함수로 옮길지 정리하는 계획 문서이다.

표의 모든 테스트 칸이 200개 이하라면 모든 테스트를 작성한다. 200개를 초과한다면 안전 모드와 자동 모드에서는 예상되는 테스트 개수를 설계자에게 보고하고 잠시 대기한다. 위임 모드에서는 테스트 범위를 세부 항목으로 나누고, 각 항목을 별도 폴더의 독립 테스트로 분리해 수행한다.

테스트 계획은 다음 기준으로 작성한다.

- 테스트는 가능하면 객체별로 파일을 분리한다.
- UniTest 프레임워크를 사용할 경우, 테스트 단계와 파일 구성을 어떻게 작성할지 개괄적인 계획을 적는다.
- UniTest 프레임워크를 사용하지 않을 경우, 표에 기반하여 실행할 테스트들의 개괄적인 계획과 목록을 적는다.
- 단위 테스트와 통합 테스트를 구분하고, 통합 테스트는 대표 유스케이스와 실패 시나리오를 중심으로 계획한다.

## 5. 테스트 코드 작성

테스트 계획에 따라 테스트 파일을 작성하거나 수정한다. 일반 테스트 코드는 해당 모듈 또는 유닛의 기존 테스트 프로젝트에 둔다.
UniTest 기반 테스트를 추가할 때는 해당 코드 위치에 기존 `Test` 또는 `Tests`가 있으면 그 아래의 `UniTest`를 사용하고, 없으면 바로 `UniTest`를 생성한다.
이 저장소의 기존 `Tests.Unit`과 `Tests.Recursion` 코드 배치는 유지한다.
테스트 코드 폴더에는 코드만 두고, 상태표·계획·결과 문서는 2번에서 정한 문서 폴더에 함께 둔다.

도메인별 테스트 프로젝트는 UniTest 저장소 안에 추가하지 않고 해당 도메인 폴더가 직접 소유한다.

기존 테스트 프로젝트가 있으면 재사용하고, 새 테스트 집합은 `모듈명.Tests.csproj` SDK 프로젝트로 분리한다.
같은 저장소의 테스트 대상 소스는 복제하지 않고 `ProjectReference`로 연결한다.
소비 저장소는 로컬 피드의 검증된 `BlackThunder.UniTest` 안정 패키지를 정확한 버전 범위로 고정하여 참조한다.
UniTest 자체 개발용 테스트와 샘플은 소스 프로젝트 참조를 유지한다.

패키지 보관 위치와 피드 구성은 [README 설치 안내](../../README.ko.md)를 따른다.
패키지의 원본 커밋·SHA-256·검증 결과를 기록하고 같은 버전의 패키지를 덮어쓰지 않는다.
검증된 자사 `.nupkg`만 버전 관리하며, 복원된 의존성이나 생성된 DLL은 포함하지 않는다.
소비 저장소는 외부 UniTest 개발 저장소 없이도 복원과 실행이 가능해야 한다.

프로젝트 설정은 해당 저장소의 `.csproj`, `Directory.Build.props`, `NuGet.config`와 CI를 기준으로 한다.
대상 프레임워크와 언어 설정은 [C# 플랫폼 기준](../../blackthunder-conventions/instructions/플랫폼%20기준%20-%20CSharp.md)을 따르며, 공통 설정을 프로젝트별로 중복 정의하지 않는다.

POCO 테스트는 `dotnet test`로 실행할 수 있도록 구성한다.
NUnit 기반 테스트는 기존 NUnit 3 구성을 유지하며, `Microsoft.NET.Test.Sdk`와 `NUnit3TestAdapter`로 테스트를 발견하고 실행한다.
일반 값 검증은 `Assert.That(..., Is/Has/Does/Contains...)`, 예외 검증은 `Assert.Throws` 또는 `Assert.ThrowsAsync`를 사용한다.
NUnit 4 전용 API나 `NUnit.Framework.Legacy`는 사용하지 않는다.
UniTest의 실행 모드와 스레드 제약은 [구현](02.%20Implementations.md)의 실행 모드 절을 따른다.

각 테스트 함수에는 짧은 주석을 작성하여, `01. Tables.md`와 `02. Plans.md`의 어떤 단계 또는 칸에 해당하는 테스트인지 알아볼 수 있게 한다.

테스트를 작성한 뒤에는 완성된 테스트와 계획 문서를 대조한다.

- 계획에서 누락된 테스트가 있다면 테스트를 추가한다.
- 구현 중 추가되거나 변경된 테스트가 있다면 `02. Plans.md`에 반영한다.
- 테스트 코드가 현재 표와 맞지 않는다면 먼저 표 또는 계획의 기준을 갱신한 뒤 코드를 맞춘다.

## 6. 빌드와 실행

테스트 코드를 빌드하고 실행한다. 자동 실행이 불가능하면 제약과 미실행 항목을 설계자에게 보고한다.

저장소의 검증 범위 지침에 따라 실행 대상을 정하고, 현재 프로젝트와 CI에 정의된 명령으로 복원·빌드·테스트를 수행한다.
POCO 테스트는 필요한 의존성을 복원한 뒤 `dotnet test`로 실행하며, 결과 경로는 2번의 문서 배치 기준을 따른다.
실제로 실행된 테스트 수와 성공·실패·건너뜀을 확인한다. 테스트가 발견되지 않은 경우에는 검증 완료로 처리하지 않고 원인과 미실행 범위를 기록한다.

이 저장소의 기본 `dotnet test` 결과 경로는 프로젝트별로 나뉜다. Unit 프로젝트는 `Tests/Unit/`,
Recursion 프로젝트는 `Tests/UniTest/`를 사용하며 두 경로의 기준은 `docs/Wiki.ko`이다.
전체 프로젝트 실행에서는 이 기본값을 사용하고, 산출물 파일명에 날짜·시간과 목적을 붙인다.
다음 명령은 저장소 루트에서 사용하는 예시이다.

```powershell
$testRunStamp = Get-Date -Format 'yyyyMMdd-HHmmss'
dotnet test tests/BlackThunder.UniTest.Tests.Unit/BlackThunder.UniTest.Tests.Unit.csproj --configuration Release --logger "trx;LogFileName=$testRunStamp-unit-all.trx"
dotnet test tests/BlackThunder.UniTest.Tests.Recursion/BlackThunder.UniTest.Tests.Recursion.csproj --configuration Release --logger "trx;LogFileName=$testRunStamp-unitest-all.trx"
```

모듈별 검증과 보고를 위한 실행은 `--filter`와 `--results-directory`를 함께 명시하는 다음 방식을 기본으로 한다.
필터는 보고할 모듈의 실제 fixture 범위를 선택해야 하며, 출력 경로만 모듈 폴더로 바꾸어 전체 테스트를 실행하지 않는다.
한 모듈에 여러 fixture가 속하면 그 모듈의 범위 전체를 선택한다. 실행 로그도 TRX와 같은 모듈 폴더에 저장한다.
다음은 일반 Model 테스트와 UniTest 기반 Model 테스트를 각각 단독 실행하는 예시이다.

```powershell
$testRunStamp = Get-Date -Format 'yyyyMMdd-HHmmss'
dotnet test tests/BlackThunder.UniTest.Tests.Unit/BlackThunder.UniTest.Tests.Unit.csproj --configuration Release --filter 'FullyQualifiedName~BlackThunder.UniTest.Tests.Unit.ModelTest' --results-directory docs/Wiki.ko/Tests/Unit/Model --logger "trx;LogFileName=$testRunStamp-model-unit.trx"
dotnet test tests/BlackThunder.UniTest.Tests.Recursion/BlackThunder.UniTest.Tests.Recursion.csproj --configuration Release --filter 'FullyQualifiedName~BlackThunder.UniTest.Tests.Recursion.ModelTest' --results-directory docs/Wiki.ko/Tests/UniTest/Model --logger "trx;LogFileName=$testRunStamp-model-unitest.trx"
```

전체 솔루션을 한 번에 실행할 때도 프로젝트별 기본 출력 위치를 유지한다.
전체 빌드·통합 실행을 기록하는 로그는 실행 날짜·시간과 목적을 담은 이름으로 `docs/Wiki.ko/Tests/` 바로 아래에 둔다.

테스트 실행 중 실패가 발생하면, 실패한 테스트가 표의 어떤 칸과 계획의 어떤 항목에 대응하는지 먼저 확인한다.
새로 확인한 문제와 기존 문제의 상태 변경은 공통 `Issues.md`에 반영한다.

실패 이후의 보고, 수정, 대기 여부는 1번에서 선택한 모드를 따른다.

## 7. 결과 기록과 통합 테스트

실행 도중 확인한 문제의 상세 근거는 해당 상태표·계획과 같은 문서 폴더의 `03. Results.md`에 기록하고, 공통 `Issues.md`에 요약과 링크를 남긴다.
여러 모듈의 통합 실행 요약은 공통 테스트 문서 폴더에 기록하고 모듈별 결과로 연결한다.
모듈별 결과 문서에는 그 모듈만 실행한 명령·사례 수와 같은 폴더의 TRX·로그를 연결한다.
전체 실행의 과거 기록이나 추가 통합 검증은 별도 근거로 구분하여 연결한다.

기록 대상은 다음과 같다.

- 빌드 또는 실행 명령
- 실행된 테스트 수와 성공·실패·건너뜀 결과
- SDK 또는 CLI 환경의 제약
- 실패 원인과 후속 조치
- 표, 계획, 코드 사이의 정합성 보강 내용

`Issues.md`는 다음 기준으로 작성하고 작업을 마칠 때 최신 결과와 대조하여 갱신한다.

- 미해결 문제와 사용자 확인이 필요한 항목을 먼저 보여 주고, 해결된 항목은 별도 이력으로 구분한다.
- 확인된 런타임 결함, 테스트 작성 문제, 실행 환경 제약, 추가 보강 검토를 구분한다. 미검증 범위나 보강 후보를 확인된 결함으로 기록하지 않는다.
- 각 항목에는 식별 ID, 대상 모듈, 현재 상태, 문제와 영향의 요약, 다음 확인·조치, 마지막 확인 날짜, 상세 결과 문서 링크를 기록한다. 실패 항목의 재현 조건과 기대·실제 결과는 상세 결과 문서에서 확인할 수 있어야 한다.
- 같은 원인에서 나온 여러 실패는 한 항목으로 묶고, 관련 테스트·시나리오 ID를 연결한다.
- 수정만 하고 재실행하지 않았다면 '재검증 대기'로 남긴다. 해결 상태로 바꿀 때는 검증 날짜와 실제 재실행 결과를 연결한다.
- 확인된 미해결 문제가 없더라도 파일을 유지하고, 확인한 범위와 날짜를 함께 적는다. 실행하지 못한 범위는 별도로 표시한다.

모듈 또는 유닛 테스트가 완료되면 대표 유스케이스와 실패 시나리오를 포함해 통합 테스트를 수행한다.
통합 테스트의 실행, 보고, 대기 방식도 1번에서 선택한 모드를 따른다.
통합 실행에서 문제 상태가 달라지면 모듈의 `03. Results.md`, 공통 실행 요약과 `Issues.md`를 함께 갱신한다.
