# UniTest Test Authoring Workflow

This document defines the workflow agents follow when creating or strengthening ordinary unit tests and UniTest-based self-tests.

## Contents

1. Select a Mode
2. Prepare Test Documentation Folders
3. Write State–Action Tables
4. Write Test Plans
5. Write Test Code
6. Build and Run
7. Record Results and Run Integration Tests

## 1. Select a Mode

Before authoring tests, check which mode the designer has selected. Use Safe Mode by default if no mode is specified.

| Mode | Response to failures or design errors |
| --- | --- |
| Safe Mode | Report the cause and proposed fix to the designer and wait when a test fails. |
| Automatic Mode | Fix the test code or target code directly when a test fails. Report to the designer and wait only for a major design error that requires an API change. |
| Delegated Mode | Change code and documentation independently even when an API change is needed, then report the changes and results when the work is complete. |

The mode determines the scope of failure handling. All modes retain the same basic workflow of writing state–action tables, planning tests, implementing tests, and recording execution results.

## 2. Prepare Test Documentation Folders

Keep state–action tables, test plans, and execution results together in the wiki's test documentation location, separate from test code.
First choose a base folder according to the existing documentation structure.

- If an object has its own documentation folder, use that folder as the base.
- If there is no object-specific documentation, use the nearest shared documentation folder. This also applies when design documents are individual files in a shared folder without separate object-specific folders.
- For plans and overall results spanning multiple objects, use their shared documentation folder as the base.

Classify documentation by how tests are structured. `Unit` contains ordinary unit tests that verify the target API directly,
while `UniTest` contains self-tests that use UniTest's Project and Lab to generate and execute paths.
Both can be discovered and run by NUnit, so NUnit usage does not determine the category.

Apply the same placement rules to object-specific and shared folders.
If the base folder already contains `Test` or `Tests`, preserve that name and place ordinary tests under `Unit` and self-tests under `UniTest`.
If there is no existing test folder and only UniTest-based tests are managed, `UniTest` may be created directly under the base folder.
When ordinary tests are also managed, create `Tests` and separate the two categories. Move any existing direct `UniTest` folder to `Tests/UniTest` and update related links.
Determine the code and documentation folder structures independently.

| Existing structure and managed scope | Ordinary test documentation | UniTest-based test documentation |
| --- | --- | --- |
| No test folder; only UniTest-based tests | Not applicable | `<base folder>/UniTest` |
| No test folder; ordinary tests also managed | `<base folder>/Tests/Unit` | `<base folder>/Tests/UniTest` |
| Existing `Test` folder | `<base folder>/Test/Unit` | `<base folder>/Test/UniTest` |
| Existing `Tests` folder | `<base folder>/Tests/Unit` | `<base folder>/Tests/UniTest` |

At a shared location, group each target's tables, plans, and results under `Unit/<target>` or `UniTest/<target>`.
If both approaches verify the same object, keep their documentation separate. Link shared contracts, but record the scope verified by each test suite separately.

This repository keeps Korean design documents as files directly under `docs/Wiki.ko`, so the existing `Tests` folder serves as the shared test documentation folder.

| Location | Managed content |
| --- | --- |
| `docs/Wiki.ko/Tests/Unit/<target>` | Ordinary tests in `BlackThunder.UniTest.Tests.Unit` |
| `docs/Wiki.ko/Tests/UniTest/<target>` | UniTest-based self-tests in `BlackThunder.UniTest.Tests.Recursion` |
| `docs/Wiki.ko/Tests/Result.md` | Shared structure and overall execution results for both test projects |

Target-specific documents are linked from the [overall structure and results](Tests/Result.md).
Test documentation is generally divided into these files.

| File | Role |
| --- | --- |
| `01. Tables.md` | State–action tables for each module |
| `02. Plans.md` | Mapping from state–action tables to test files and methods, and the execution plan |
| `03. Results.md` | Significant issues observed during execution and the result record |

When documenting existing tests, distinguish implemented coverage from future improvements.
Do not confuse contract groups in a table with executed cases after NUnit parameter expansion.
When reorganizing existing execution records, state their execution dates and evidence rather than presenting them as new runs.

Place a shared execution summary spanning multiple targets or both test categories in `Result.md` in the shared test documentation folder.
Link to module-specific tables, plans, and defect records instead of duplicating their details.

Store TRX files and execution logs according to the scope actually executed, as follows. Do not create a separate `Results` folder or a results folder at the repository root.

| Actual execution scope | Raw artifact location |
| --- | --- |
| One ordinary test module | Beside its documents in `docs/Wiki.ko/Tests/Unit/<module>/` |
| One UniTest-based test module | Beside its documents in `docs/Wiki.ko/Tests/UniTest/<module>/` |
| TRX for the entire Unit project | Directly under `docs/Wiki.ko/Tests/Unit/` |
| TRX for the entire Recursion project | Directly under `docs/Wiki.ko/Tests/UniTest/` |
| Full build and integrated execution logs | Directly under `docs/Wiki.ko/Tests/` |

Choose the location based on actual execution scope, not the command's working directory or the report's subject.
For module verification and reporting, filter the run to that module and store its TRX and log beside the module's documents by default.
Each module's `03. Results.md` directly links to its own TRX and log using relative links within the same folder.
For example, keep Lab's actual artifacts and documents together in `Tests/Unit/Lab/` or `Tests/UniTest/Lab/`.

When integration verification requires a whole-project TRX, store it at the location for that execution scope.
When removing old artifacts, remove their links as well and retain only the necessary execution figures and defect analysis as documentation history.
Do not copy or split a whole-project TRX into a specific module; module documents may link to it as supplementary evidence when needed.
Adding only a shared link to a whole-project TRX does not complete module-specific artifact organization.

Use filenames that identify the execution date and purpose, and include the time when repeating the same purpose on the same date. Examples are `20261107-001145-unit-all.trx`,
`20261107-001145-model-unit.trx`, and `20261107-001145-build.log`.
Existing automatically generated TRX names may be retained if they identify the execution time.
Keep generated TRX files and logs excluded by `.gitignore`; only summary documents provide relative links to the raw artifacts.
Preserve both original contents and related links when moving files.

## 3. Write State–Action Tables

Write a state–action table for each module or unit in `01. Tables.md`. If `01. Tables.md` already exists, review and strengthen it against the current implementation and public API.

Follow the [UniTest state–action guideline](00.%20Unit%20Test%20Guideline.md) for the table's format and meaning.

## 4. Write Test Plans

Create `02. Plans.md` from the state–action tables before writing or modifying test code. This plan maps table cells to test files and test functions.

If the tables contain no more than 200 test cells in total, implement all tests. If there are more than 200, report the expected test count to the designer and pause in Safe Mode or Automatic Mode. In Delegated Mode, divide the scope into smaller items and execute each as an independent test in a separate folder.

Write the test plan according to these rules.

- Separate test files by object where possible.
- When using UniTest, outline the test stages and file organization.
- When not using UniTest, outline and list the tests to execute based on the tables.
- Distinguish unit tests from integration tests, and plan integration tests around representative use cases and failure scenarios.

## 5. Write Test Code

Create or modify test files according to the test plan. Keep ordinary test code in the module's or unit's existing test project.
When adding UniTest-based tests, use `UniTest` under an existing `Test` or `Tests` folder at that code location; otherwise create `UniTest` directly there.
Preserve this repository's existing `Tests.Unit` and `Tests.Recursion` code layout.
Keep only code in test code folders; keep tables, plans, and results together in the documentation folder selected in section 2.

Domain-specific test projects belong directly to their domain folders rather than being added inside the UniTest repository.

Reuse existing test projects, and separate new test suites into `ModuleName.Tests.csproj` SDK projects.
Reference the source under test in the same repository with `ProjectReference` rather than duplicating it.
Consuming repositories reference a verified stable `BlackThunder.UniTest` package from their local feed, pinned to an exact version range.
Tests and samples used to develop UniTest itself retain source project references.

Follow the [README installation instructions](../../README.md) for package storage and feed configuration.
Record the package's source commit, SHA-256, and verification results, and do not overwrite a package with the same version.
Version only verified first-party `.nupkg` files, excluding restored dependencies and generated DLLs.
Consuming repositories must be able to restore and run without an external UniTest development checkout.

Use the repository's `.csproj`, `Directory.Build.props`, `NuGet.config`, and CI as the authority for project settings.
Follow the [C# platform baseline](../../blackthunder-conventions/instructions/플랫폼%20기준%20-%20CSharp.md) for target frameworks and language settings; do not duplicate shared settings in individual projects.

Configure POCO tests to run with `dotnet test`.
Keep the existing NUnit 3 setup for NUnit-based tests, using `Microsoft.NET.Test.Sdk` and `NUnit3TestAdapter` for discovery and execution.
Use `Assert.That(..., Is/Has/Does/Contains...)` for ordinary value assertions and `Assert.Throws` or `Assert.ThrowsAsync` for exceptions.
Do not use NUnit 4-only APIs or `NUnit.Framework.Legacy`.
Follow the execution modes section of [Implementation](02.%20Implementations.md) for UniTest's execution modes and threading constraints.

Add a short comment to each test function identifying the stage or cell in `01. Tables.md` and `02. Plans.md` that it covers.

After implementing tests, compare the completed tests with the plan.

- Add any tests missing from the plan's implementation.
- Reflect tests added or changed during implementation in `02. Plans.md`.
- If the test code no longer matches the current tables, update the table or plan criteria first, then align the code.

## 6. Build and Run

Build and run the test code. If automated execution is unavailable, report the constraints and unexecuted items to the designer.

Select the execution scope according to the repository's verification guidelines, then restore, build, and test with the commands defined by the current projects and CI.
Restore required dependencies before running POCO tests with `dotnet test`, and follow section 2 for result locations.
Check the number of tests actually executed and the passed, failed, and skipped counts. If no tests are discovered, do not mark verification complete; record the cause and unexecuted scope.

This repository separates default `dotnet test` result locations by project. The Unit project uses `Tests/Unit/`,
and the Recursion project uses `Tests/UniTest/`, both relative to `docs/Wiki.ko`.
Use these defaults for whole-project execution, and include the date, time, and purpose in artifact names.
The following examples run from the repository root.

```powershell
$testRunStamp = Get-Date -Format 'yyyyMMdd-HHmmss'
dotnet test tests/BlackThunder.UniTest.Tests.Unit/BlackThunder.UniTest.Tests.Unit.csproj --configuration Release --logger "trx;LogFileName=$testRunStamp-unit-all.trx"
dotnet test tests/BlackThunder.UniTest.Tests.Recursion/BlackThunder.UniTest.Tests.Recursion.csproj --configuration Release --logger "trx;LogFileName=$testRunStamp-unitest-all.trx"
```

For module-specific verification and reporting, explicitly specify both `--filter` and `--results-directory` as shown below.
The filter must select the actual fixtures belonging to the module being reported. Do not run the full suite while merely changing the output location to a module folder.
If a module contains multiple fixtures, select its entire scope. Store the execution log in the same module folder as the TRX.
The following examples run the ordinary Model tests and UniTest-based Model tests separately.

```powershell
$testRunStamp = Get-Date -Format 'yyyyMMdd-HHmmss'
dotnet test tests/BlackThunder.UniTest.Tests.Unit/BlackThunder.UniTest.Tests.Unit.csproj --configuration Release --filter 'FullyQualifiedName~BlackThunder.UniTest.Tests.Unit.ModelTest' --results-directory docs/Wiki.ko/Tests/Unit/Model --logger "trx;LogFileName=$testRunStamp-model-unit.trx"
dotnet test tests/BlackThunder.UniTest.Tests.Recursion/BlackThunder.UniTest.Tests.Recursion.csproj --configuration Release --filter 'FullyQualifiedName~BlackThunder.UniTest.Tests.Recursion.ModelTest' --results-directory docs/Wiki.ko/Tests/UniTest/Model --logger "trx;LogFileName=$testRunStamp-model-unitest.trx"
```

Keep the project-specific default output locations when running the entire solution at once as well.
Store full build and integrated execution logs directly under `docs/Wiki.ko/Tests/`, with the execution date, time, and purpose in the filename.

When a test fails during execution, first identify the corresponding table cell and plan item.
Reflect newly identified issues and status changes to existing issues in the module's `03. Results.md`.

Follow the mode selected in section 1 for reporting, fixing, or waiting after a failure.

## 7. Record Results and Run Integration Tests

Record detailed evidence for issues observed during execution in `03. Results.md` beside the corresponding tables and plans.
Record integrated execution summaries spanning multiple modules in the shared test documentation folder and link to module-specific results.
Each module result document links its module-only command, case count, and the TRX and log in the same folder.
Distinguish historical full-suite records and additional integration verification as separate evidence.

Record the following information.

- Build or execution commands
- Number of tests executed and passed, failed, and skipped results
- SDK or CLI environment constraints
- Failure causes and follow-up actions
- Improvements to consistency between tables, plans, and code

Record test issues in `03. Results.md` according to these rules, checking them against the latest results before completing the work.

- Show unresolved issues and items requiring user review first, and separate resolved items into a history section.
- Distinguish confirmed runtime defects, test implementation issues, execution environment constraints, and proposed coverage improvements. Do not describe unverified scope or improvement candidates as confirmed defects.
- Record each item's current status, a summary of the issue and its impact, the next check or action, and the last verification date. For failures, also record reproduction conditions and expected versus actual results.
- Group multiple failures with the same cause into one issue and link their test and scenario IDs.
- If a fix has not been rerun, leave its status as 'Awaiting revalidation'. When marking it resolved, link the verification date and actual rerun results.
- Mark unexecuted scope separately.

After module or unit tests are complete, run integration tests that cover representative use cases and failure scenarios.
Follow the mode selected in section 1 for executing, reporting, or waiting on integration tests as well.
If an integration run changes an issue's status, update the module's `03. Results.md` and the shared execution summary together.
