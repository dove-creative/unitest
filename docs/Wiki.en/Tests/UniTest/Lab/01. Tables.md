## Scope

These enhancements preserve the 133 existing Lab self-test scenarios while verifying actual execution and state preservation across repeated execution.
The execution modes are Inline and ThreadPool, and the target code is not changed.

## Existing scenarios

There are 31 condition combinations after excluding unnecessary combinations following the first failure. Each combination is executed with and without constructor metadata,
giving 62 execution checks and 62 copy checks. The contracts covered by the existing scenarios are grouped into the following five cells.

| ID | Input/action | Expected result |
| --- | --- | --- |
| LB-M01 | Execute with a null model | Model setup failure is reported as ExecutionException |
| LB-M02 | 62 success/failure combinations across metadata, arrange, act, and assert stages | Preserve the existing expectations for exceptions, continuability, and remaining execution count |
| LB-M03 | 2 metadata-passing cases using a constructor or delegate | Pass the specified metadata values |
| LB-M04 | 6 remaining-execution-count merge cases | Handle unlimited execution and choose the smaller limit |
| LB-M05 | 62 Lab copy combinations | Replace the ID while preserving delegates and metadata settings |

## Repeated execution

States distinguish whether a preceding execution exists. The accumulated integer and execution count are verification data.
Add2 and Subtract1 are small Labs that add 2 to or subtract 1 from an integer, respectively; the same instances are reused.

| State | - | Add2 | Subtract1 |
| --- | --- | --- | --- |
| | - | Add 2 to the integer | Subtract 1 from the integer |
| | - | | |
| Initial execution | - | LB-R01: **Repeatable**, `[metadata creation, stage order, one history entry]` | LB-R02: **Repeatable**, `[metadata creation, stage order, one history entry]` |
| Repeatable | - | LB-R03: `[previous metadata removed, fresh metadata, accumulated value, ordered history]` | LB-R04: `[previous metadata removed, fresh metadata, accumulated value, ordered history]` |

Each execution follows SetMetadata → Arrange → Act → Assert. Odd-numbered executions specify an expected exception during arrangement
and throw it during the action; even-numbered executions must have no expected exception.
This also verifies that metadata from a preceding execution does not leak into the next execution or the original template.

## Execution guarantees

| ID | Input/action | Expected result |
| --- | --- | --- |
| LB-G01 | Run the existing scenario project at depth 1 | Exactly one occurrence of each of the 133 IDs in the independent list, all Success, execution count 1 for every model |
| LB-G02 | Exhaustive and continuous execution of the small repetition project | Execute 14 nodes exhaustively at depth 3 or 16 nodes continuously at depth 8; all nodes are Success, and each path's value, history, and stage count match |
| LB-G03 | Inject an incorrect accumulated-value expectation into the repetition project | The executed node is Failure and the actual assertion exception is preserved |

The full scope consists of 12 cells: 5 existing-scenario cells, 4 repeated state-action cells, and 3 execution-guarantee cells.
The 133 scenarios are not branched across multiple depths; repeated-execution verification uses only two actions.
