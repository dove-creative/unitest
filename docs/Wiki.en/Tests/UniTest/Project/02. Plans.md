# Project self-test plan

## Structure

The implementation is [ProjectTest.cs](../../../../../tests/BlackThunder.UniTest.Tests.Recursion/UniTest/ProjectTest.cs). It uses the existing Recursion project's source reference and NUnit runner.

The outer `ScenarioProject` generates each verification as a `Lab<Model>`. Each Lab executes and checks a small inner `CounterProject`. Synchronous Lab callbacks wait for asynchronous execution on outer ThreadPool workers. No sleeps or timing assumptions establish execution order.

## Table-to-code mapping

| Table | Method | Verification |
| --- | --- | --- |
| P01 | `VerifyDepth` | Compare independently enumerated paths, arithmetic values, separate model instances, and ProcessCount |
| P02 | `VerifyReplay` | Compare path prefixes and exhaustive traversal |
| P03 | `VerifyContinuous` | Validate candidates and expanded branches, repeat seeds across modes, and replay a longest path |
| P04 | `VerifyNoContinuation` | Check depth and continuous runs with empty and terminal-only generators |
| P05 | `VerifyFailure` | Check explicit failures, underlying exceptions, and halted expansion at all entry points |
| P06 | `VerifyContinueAfterFailure` | Check failing siblings alongside successful descendants and failure-report scope |
| P07 | `VerifyGeneratorFailure`, `VerifyUnknownPath` | Verify partial generation preservation and invalid-path exceptions |
| P08 | `VerifyExternalCancellation` | Check zero user-code calls and reuse rejection for all entry points |
| P09 | `VerifySingleUse` | Reject all entry points after the first execution and preserve snapshots after cancellation |
| P10 | `VerifyCancelledProject` | Repeated Cancel and rejection by every execution entry point |

## Execution and completeness

`ProjectScenarios` executes 26 scenarios at depth 1 for each of `ThreadPool` and `Inline`. Final checks cover the full Lab ID set, count, successful status, and processed count. Empty graphs or missing scenarios cannot pass.

P02, P03, P06, and P07 integrate execution, Node, Model, and reports. Run the new tests without modifying production code first. If they reveal a real implementation defect, record the cause and failure under the safe-mode workflow.
